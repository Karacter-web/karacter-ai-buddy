## 1. WHAT IS BEING BUILT

Karacter AI is a voice-first Progressive Web Application (PWA) assistant that 
operates through a capability registry system. Unlike traditional assistants with 
hardcoded integrations, Karacter discovers available capabilities at runtime and 
plans intents against only those that are connected by the user.

Core functionality:
- Voice input via wake word detection ("Hey Karacter") or manual tap-to-talk
- Natural language processing through Lovable AI Gateway (Google Gemini 3.6 Flash)
- Intent planning: transforms user utterances into structured intents mapped to capabilities
- Capability execution: browser-based actions (camera, clipboard, share, vibration) 
  and cloud-based integrations (Google Calendar, Spotify, GitHub, etc.)
- Conversation persistence in Supabase with full history and replay
- User profile management with biometric enrolment (voice/face signatures)
- Runtime capability registry: users can connect/disable/configure integrations without redeploy
- Audit logging of all executed intents
- Continuous learning: distills durable facts from conversations into memories
- Multi-factor authentication: Supabase auth + optional biometric verification
- PWA features: install prompt, offline support, manifest

Target deployment: Cloudflare Workers behind karacterhub.xyz

**Architecture patterns:**

- Event-driven: Custom events for wake word, camera, notifications

### Data Flow

**Frontend → Backend → DB/External APIs:**

1. User speaks/types → capture by useVoice.ts or Input component
2. Utterance submitted to planUtterance server function (src/lib/karacter/plan.functions.ts)
3. Server function calls Lovable AI Gateway via chatJson() (src/lib/karacter/ai.server.ts)
4. AI returns structured JSON with speech response and intents array
5. Intents mapped to capabilities and executed via executeIntent() (src/lib/karacter/executor.ts)
6. Execution results logged to Supabase intent_logs table
7. Conversations and messages persisted to Supabase conversations/messages tables
8. Query invalidation triggers React Query refetch for UI updates

**Auth Flow:**
1. User signs in via Supabase Auth (email/password or Google OAuth)
2. Session stored in localStorage via supabase client
3. attachSupabaseAuth middleware attaches Bearer token to server function requests
4. requireSupabaseAuth middleware validates token and extracts user context on server
5. User context (userId, claims) available to server functions for authorization

**Capability Registry Flow:**
1. Capabilities loaded from Supabase capabilities table (read-only, public)
2. User integrations loaded from integrations table (user-scoped)
3. Available capabilities = capabilities ∩ enabled integrations
4. Planner receives only available capabilities to prevent planning for disconnected tools

### Auth/Authorization Model (as implemented)

**Primary:** Supabase Auth with email/password and Google OAuth
- Session persistence via localStorage
- CSRF protection via createCsrfMiddleware in start.ts
- Row Level Security (RLS) on all Supabase tables
- User-scoped data access (auth.uid() = user_id policies)

**Secondary (currently disabled):** Biometric verification
- Voice signature: FFT magnitude envelope, 48 bins, averaged across samples
- Face signature: 16x16 grayscale contrast-normalized vector
- Thresholds: VOICE_THRESHOLD = 0.9, FACE_THRESHOLD = 0.72
- Paused by default (require_voice_match = false, require_face_match = false in onboarding)
- Can be enabled per-user but verification system is flagged as unstable

**Server-side security:**
- requireSupabaseAuth middleware: Validates JWT token, extracts claims
- Server functions protected by middleware chain
- Admin operations use supabaseAdmin client with SUPABASE_SERVICE_ROLE_KEY
- No explicit RBAC beyond user ownership (RLS handles data access)

## 7. HONEST SUMMARY

Karacter AI is **further along than its commit history suggests** in terms of core 
functionality. The authentication system, chat persistence, capability registry, 
intent planning, and basic execution are all wired end-to-end and would work in 
a properly configured deployment. The codebase shows thoughtful architecture 
with clean separation of concerns, proper TypeScript usage, and consistent patterns.

However, the project is **significantly further behind than it appears** in terms 
of security and production readiness. The single biggest risk is the committed .env 
file with Supabase credentials, which represents a critical security vulnerability that 
must be addressed immediately. Beyond that, the biometric verification system—while 
built—is completely disabled and unwired, meaning the "opt-in step-up" security model 
described in the ROADMAP simply doesn't exist in practice. Agent capabilities are 
stubbed placeholders, and there's no test coverage to prevent regressions.

The most honest assessment: **approximately 70% of the claimed functionality is actually 
working and wired**, but the remaining 30% includes critical security features (biometric 
verification, rate limiting) and production concerns (secrets management, testing) 
that make this unsuitable for production deployment in its current state. The core 
assistant experience (speak → plan → execute browser capabilities) is genuinely solid 
and well-implemented; everything beyond that needs hardening before going live.

Biggest current risks:
1. Committed secrets (CRITICAL)
2. Unsafe code evaluation (CRITICAL)
3. Missing rate limiting (HIGH)
4. Disabled biometric security (HIGH)
5. No test coverage (MEDIUM)

The project has excellent bones and a sophisticated architecture. With a focused 
effort on the critical and high-priority items above, it could be production-ready 
within 2-3 weeks of concentrated work.
